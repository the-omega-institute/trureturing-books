# Content accuracy review

Use this skill for chapter-level accuracy work in this repository. The deliverable is a small, reviewable batch: confirmed corrections in both languages, an honest coverage record, independent validation, and a timely PR. Preserve the requested scope. Do not turn a chapter review into a rewrite or mark unreviewed units as complete.

At the start of each assignment or recovery, read the current `AGENTS.md`, `PROJECT.md`, `docs/project/WORKFLOW.md`, and relevant verification guidance. Recover the authorized slice, candidate input, prior evidence and pending obligations before editing. Chinese is authoritative; English must be natural and semantically aligned. Preserve the author’s epigraphs and distinctive prose using [references/style-preservation.md](references/style-preservation.md).

Use the assigned workspace and respect the assignment’s implementation and Git lifecycle ownership. A bounded repair can finish with an uncommitted, reviewable patch; creating a worktree, rebasing, pushing or opening a PR belongs to the authorized lifecycle owner. Treat `trureturing.lock.json` as tool-owned: use `./tbook pin` only when a pin operation is required and authorized, and never hand-edit the lock. Keep the current pin, its configured branch, and historical audit pins distinct.

For a new chapter audit, perform the complete reading below. For a resumed repair, compare current inputs with the cited evidence first, then repair and validate the affected claims and context. Historical text coverage, changed/new media coverage, output evidence and lifecycle status are separate records. New media do not inherit approval from unchanged prose, and a passing build does not establish content accuracy. Reuse evidence only with an explicit comparison of its relevant text, source/pin, media and tooling dependencies; recheck what changed. A dependency update alone does not require a full-book audit. See [references/review-protocol.md](references/review-protocol.md) for recording this boundary.

For a full audit, apply all steps to each requested unit. For a bounded repair, apply steps 1–3 to the affected claims and their dependencies, retaining the documented unchanged evidence:

1. Read the complete Chinese and English chapter, every formal block and proof, every formula/table/example, and every shared image or interactive reference. Start a coverage row before editing.
2. Extract all `lean` GIDs and compare each formal environment with the frozen declaration at the current pin: name, kind, module, assumptions, types, domains, quantifiers, conclusion, and the scope of the prose proof. Formal theorem-like environments must resolve to lock entries of `kind = theorem`. When relating a theorem to a sampled construction, preserve its optimization or existence quantifiers: an attainable optimum need not be attained by the displayed sample. Read each media green evidence box in full against its cited statement: a valid GID does not verify accompanying consequences; manual instantiations and derivations retain their own attribution outside the verified box.
3. Independently recompute material numerical claims and inspect literature attribution, physical protocol assumptions, and epistemic level. Separate Lean results, literature results, author interpretation, and open questions. Record unresolved provenance as a limitation instead of silently strengthening the text.
   For quantitative claims, trace the stated bound or behavior across the actual supported control domain and every existing reader-facing consumer; do not infer the mathematical domain from a preset, display range, or a severely truncated example.

When reviewing interactive controls, treat combinations of controls and selector precedence as part of the supported domain: a preset can set several controls, and later reader changes can override one while leaving the others in force. A note, caption or readout that stays visible after such an override must hold for the overridden state: qualify a fixed example with its preset condition or state the general expression, and keep the correct example. A label must name both the observable and the statistic shown: an outcome probability such as P(Z = +1) is not the expectation ⟨Z⟩, so a correct number under the wrong statistic is fixed by relabelling it, not by changing the number. If a lock or intake excerpt shows a truncated declaration signature, compare it with the complete exact-pin declaration before changing a correct assertion.
4. Classify findings as confirmed, advisory, or discarded. Fix only confirmed inaccuracies and necessary bilingual mismatches. Edit Chinese first, then make the English accurate and idiomatic. Keep chapter order, stable IDs, GIDs, media order, and proof-boundary conventions unchanged.
5. Run the smallest meaningful checks while iterating, then validate the completed patch. At minimum use `./tbook check`; for output changes build the affected HTML/PDF/EPUB/site targets, run EPUBCheck, validate changed SVG/XML, and inspect relevant desktop/mobile and theme combinations. Changed labs also need the current project’s browser tests, visual inspection and refreshed cited stills. Record actual failures and limits. Identify evidence by input HEAD plus changed paths/digests when uncommitted, or by committed candidate when available.
6. Obtain the project’s independent architecture, quality and tests reviews through the designated review owner. An implementation handoff records review as pending when the caller owns orchestration. Every blocking finding must be closed, and approval must cover the candidate’s final relevant inputs; earlier approval is reusable only within the documented unchanged dependency boundary.
7. Update `docs/project/CONTENT-ACCURACY.md` with the pin, exact coverage, confirmed corrections, evidence, review verdicts and limits. Preserve unreviewed units as pending. Label historical evidence as historical and keep current output validation distinct from independent content approval.
8. When assigned lifecycle ownership, push and create the requested timely PR, then track CI/merge/Pages. Otherwise hand off the completed patch and exact remaining lifecycle obligations. The PR description states concrete changes, pin, validation and remaining coverage, without model or agent identifiers.

Classify remote failures by the stage that failed. When branch checks pass but PR CI fails on a merge input, compare the checked commit with the branch and integrated upstream inputs before reusing the branch result. Figures derived from chapter references or declaration counts can change after integration outside the batch. Independently recompute affected values from the integrated chapters and lock under the generator's existing rules, retain its assertions, and regenerate stale artifacts; align data, bilingual ALT and captions only where the confirmed defect requires it. Use the existing full figure/source check for the current book inputs without extending content coverage. If a workflow stops while installing a browser, font, package, or other runner dependency before checking repository content, record the exact external error, retry the failed jobs once when it is plausibly transient, and do not change the book to chase that failure. If the retry fails at the same setup stage, leave the PR open with the successful local evidence and an explicit infrastructure blocker.

A batch waiting on review, CI or merge does not halt independently authorized work. A worker assigned a bounded existing repair finishes that repair and hands it back; it does not reopen unrelated historical audits or start another batch. Keep each batch’s candidate, evidence, outstanding checks and PR status explicit. When a user or external maintainer merges a candidate, record the actual PR head, merge commit and observed CI/Pages state; merged status closes that merge lifecycle but does not accept accuracy or discharge outstanding independent review and current-output obligations. The lifecycle owner carries still-applicable obligations into bounded, reviewable follow-ups, preserving spent limits and respecting the current user-authorized audit scope, including subsequent explicit scope changes, without reopening the consolidated backlog.

Use [references/review-protocol.md](references/review-protocol.md) for finding classification, validation and handoff. After integration or a fix, update the candidate identity and compare affected dependencies before claiming evidence or approval still applies.
